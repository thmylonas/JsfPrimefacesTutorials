JSF backing bean should be serializable?
--------------------------------------------

Link: https://stackoverflow.com/questions/3372687/jsf-backing-bean-should-be-serializable

Yes, you understood it correctly. The view is basically stored in the session scope.
The session scope is in JSF backed by the Servlet's HttpSession. All session attributes are supposed to implement
Serializable, this because the average ServletContainer may persist session data to hard disk among others to be able
to share with other servers in a cluster, or to survive heavy load, or to revive sessions during server restart.
Storing raw Java objects on hard disk is only possible if the respective class implements Serializable.
Then ObjectOutputStream can be used to write them to hard disk and ObjectInputStream to read them from hard disk.
The ServletContainer manages this all transparently, you actually don't need to worry about it.
JSF is just giving a warning so that you understand the risks.

Link: https://suhasjavablog.wordpress.com/2014/05/08/jsf-managedbean-must-implement-serializable-or-not/

JSF ManagedBean MUST IMPLEMENT SERIALIZABLE OR NOT ?
Recently I was reading about serialization and I noticed that all the ManagedBean in my JSF project implements Serializable interface.

Normally, we use Serialization to send an object over the network or if the state of an object needs to be persisted to a flat file or a database.
But my managedBean was just a means to value bind the UI components. I dug deep into this topic and I think it is useful to share my findings with you all.

We need not make every ManagedBean serializable. It depends upon the Scope the ManagedBean. If you don’t want to serialize your ManagedBean, make sure the scope is ‘request’.

Instead, if you are dealing with ‘session’ scope or ‘view’ scope (even view scope is using session scope). The session scope is backed by the Servlet’s HttpSession.
All session attributes are supposed to implement Serializable because the servlet container tries to persist session data to file system
to be able to survive heavy load and/or reviving sessions during server restart.

Sometimes you might have noticed that your PostConstructs in your ManagedBean get executed on server restart. Why ?
Some containers will require you to explicitly disable session serialization (or else they will be generating exceptions).
Tomcat by default enables persisting session through server restart.

Link: https://docs.oracle.com/javaee/6/tutorial/doc/gjbbk.html

Beans that use session, application, or conversation scope must be serializable, but beans that use request scope
do not have to be serializable.

About the "action" attribute
--------------------------------

If in "h:commandButton" we do not use "f:ajax", everytime we press the "h:commandButton" the whole page will be loaded.
<h:form>
    <h:inputText .../>
    <h:commandButton action="#{backingBean.method}" .../>
</h:form>

Problem 1
-------------
If we don not follow the next solutions, this:
<h:form>
    <h:inputText .../>
    <h:commandButton action="#{backingBean.method}" .../>
</h:form>
without "f:ajax" inside <h:commandButton>, will lead to the:
"The origin server did not find a current representation for the target resource or is not willing to disclose that one exists."
This:
<h:form>
    <h:inputText .../>
    <h:commandButton action="#{backingBean.method}">
        <f:ajax>
    </h:commandButton>
</h:form>
is not causing this error.
A possible explanation is that:
Everytime we press the "h:commandButton" the whole page will be loaded, but the page cannot be found, because the JSF view
is not in directories under the "webapp" directory.

Problem 2
-------------
If we don not follow the next solutions, this:
<h:form>
    <h:inputText .../>
    <h:commandButton action="#{backingBean.method}" .../>
</h:form>
without "f:ajax", in every page reload the JS alert message appears:
"The page that you're looking for used information that you entered. Returning to that page might cause any action you
took to be repeated. Do you want to continue?"
A possible explanation is that:
Everytime we reload the page, with the load of the page the form is re-posted.

Solutions
-------------

JSF views have to be in directories under the "webapp" directory
--------------------------------------------------------------------
The JSF can work fully (display page, invoke BackingBean methods from "action" attribute by EL) ONLY if the JSF views
are in directories under the "webapp" directory.
If the JSF vies are in directories under the "WEB-INF" directory, then the only that will work from JSF is to display the
page only. Other more deep in JSF functionalities (like invoke the BackingBean methods from "action" attribute by EL)
WILL NOT work.

FacesServlet have to render the JSF views (not DispatcherServlet)
---------------------------------------------------------------------
Spring Controllers must not resolve the views (that means that DispatcherServlet must not be involved).
JSF views have to be found by FacesServlet, after they are put in directories under the "webapp" directory.
We can use Filters to filter the URI the client types, and transform it to the real path to the JSF view.

When the "action" attribute method is invoked (A)
-----------------------------------------------------

The "action" attribute method is invoked (due to all the following solutions are applied), using
or:

@Component(value = "exampleBackingBean")
//@Scope(value = WebApplicationContext.SCOPE_SESSION, proxyMode = ScopedProxyMode.TARGET_CLASS)
//@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class ExampleBackingBean implements Serializable {
}

or:

@ManagedBean(name = "exampleBackingBean")
@RequestScoped
public class ExampleBackingBean implements Serializable {
    @ManagedProperty(value = "#{commonHtmlAttributesService}")
    private CommonHtmlAttributesService commonHtmlAttributesService;
    // In ManagedBeans the ManagedProperties have to have Getters-Setters (mandatory)
}

or:

The combination proposed by the online tutorial in the link (SpringMVC integrated with JSF_v2.2 example):
Link: http://javaonlineguide.net/2015/07/jsf-2-2-spring4-integration-example-using-spring-annotations.html

@Component(value = "exampleBackingBean")
@ManagedBean(name = "exampleBackingBean")
@RequestScoped
public class ExampleBackingBean implements Serializable {
    @PostConstruct
    private void init() { /*Initialization code*/ }
}

When the "action" attribute method is invoked (B)
-----------------------------------------------------

BackingBean methods from "action" attribute can be invoked, in all the following cases:
public String backingBeanActionMethod() {
    // Code
    return null;
}
public String backingBeanActionMethod() {
    // Code
    return "";
}
public void backingBeanActionMethod() {
    // Code
}

When the "action" attribute method is invoked (C)
-----------------------------------------------------

BackingBean methods from "action" attribute can be invoked, with whatever value of "immediate" attribute.
That means in all the following cases:
<h:commandButton ...immediate="true"/>
<h:commandButton ...immediate="false"/>

About the 'Sorting/Filtering' in <p:dataTable>/<p:column>
-------------------------------------------------------------

Case_A:
-----------

If we need to implement our own 'Sorting/Filtering' code for a <p:column> (by SortViewBackingBean.sortByIdMethod()),
we need to use "f:facet" tag in this column.
In this case, the header text from the "f:facet" tag, overrides the "headerText" attribute.

<h:form>
    <p:dataTable var="car" value="#{sortViewBackingBean.cars}">
        <f:facet name="header">
             Implementing our own 'Sorting/Filtering' code
        </f:facet>
        <p:column headerText="ID" sortBy="#{car.id}">
            <f:facet name="header">
                <h:commandLink value="ID" action="#{sortViewBackingBean.sortByIdMethod}"/>
            </f:facet>
            <h:outputText value="#{car.id}"/>
        </p:column>
        <!-- Other columns -->
    </p:dataTable>
</h:form>
